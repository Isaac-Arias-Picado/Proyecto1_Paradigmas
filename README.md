## 1. Arquitectura del Proyecto
El sistema fue desarrollado utilizando el paradigma imperativo en el lenguaje C. Se organizó el código por módulos, separando la lógica del programa en múltiples archivos para mejorar el orden de trabajo y división de las tareas. Se usó un archivo `constantes.h` para agrupar todos los valores constantes, lo cual hace más sencillo el poder modificar dichos valores en todo el código a la vez y facilita poder identificar dichos valores dentro del código. 

Los módulos principales son:
*   **`main.c`**: Archivo orquestador. Se encarga de manejar el flujo principal del programa usando `procesar_carrera`, esta carga los datos de los archivos de entrada, asocia usando horarios, deetcta choques y valida los requisitos para generar el archivo final en JSON.
*   **`parser.c / parser.h`**: Módulo encargado de la ingesta de datos. Lee archivos de texto plano para extraer la información estructurada de los planes de estudio y el historial académico.
*   **`horario.c / horario.h`**: Procesa las cadenas de texto de los horarios, conviritendo el formato de horas a un valor en minutos y analisando los choques entre grupos y cursos según hora de inicio y final de las clases.
*   **`requisitos.c / requisitos.h`**: Analiza cursos elegibles según los requisitos e historial académico. Evalúa el historial del estudiante contra las dependencias del curso utilizando funciones como `correquisito_cumplido` que llama a `requisito_cumplido` para identificar casos de falta de requisitos o correquisitos para poder llevar un curso.
*   **`choques.c / choques.h`**: Implementa los algoritmos de comparación temporal. Itera sobre matrices de grupos y bloques de horarios para detectar colisiones (traslapes) entre cualquier par de cursos.
*   **`exportador.c / exportador.h`**: Módulo de salida que serializa el catálogo de cursos desde las estructuras en memoria de C hacia archivos `.json`.

## 2. Decisiones de Diseño

### 2.1 Justificación de decisiones propias y del dataset
Para mejorar el manejo de memoria en C y evitar errores como fugas de memoria, se agrupó la información en arreglos estáticos usando constantes de valor máximo posible, todo eso definido en `constantes.h`.
En cuanto al dataset de horarios, se decidió aislar la extracción de los componentes temporales utilizando delimitadores y lectura formateada (`sscanf` y `strtok`), lo que permite tolerar ligeras variaciones en los espacios en blanco del archivo original copiado de la Guía de Horarios institucional. Se utilizaron los horarios correspondientes al período 2 de 2026, sede Cartago, modalidad semestre, ya que los datos recolectados inicialmente correspondían al período 2025, pero se prefirió usar información más vigente, en este caso el periodo actual. Como la Guía de Horarios no separa el número de grupo en una columna propia, este se tuvo que extraer de la guía en una pestaña marcada con "+" en cada fila, se agregó como una columna extra al formato de entrada del parser.

### 2.2 Caso límite real encontrado y resolución
**Caso:** Validación circular o encadenada de correquisitos. 
**Problema:** Un curso "A" puede tener como correquisito un curso "B". Al igual como se maneja en el sistema de matricula del TEC, el estudiante puede matricular "A" si "B" ya está aprobado, o si "B" se puede matricular simultáneamente. Si es que "B" no se ah aprobado, se necesita hacer un análisis de sus requisitos para comprobar que efectivamente tanto "A" como "B" son posibles de llevar a la vez, de lo contrario, el curso con correquisito "A" no puede ser matriculado.
**Resolución:** En `requisitos.c` la función `correquisito_cumplido` se diseñó para no solo verificar si el correquisito está en el historial, sino también para iterar sobre los requisitos del curso correquisito. Si alguno de los requisitos del curso "B" falla, la función retorna `0`, lo cual impide la matrícula del curso "A".

### 2.3 Justificación del formato de salida
Se eligió **JSON** como formato de serialización por tratarse de un estándar jerárquico. Dado que este archivo servirá como insumo para las siguientes etapas en Racket, Prolog y Java, JSON permite anidar de forma natural la relación de uno a muchos (Un Curso -> Múltiples Grupos -> Múltiples Bloques Horarios). Utilizar un formato plano como CSV hubiera requerido duplicar excesivamente los datos del curso por cada bloque horario, complicando innecesariamente el parseo en los lenguajes funcionales y lógicos posteriores.

## 3. Estructuras de Datos Desarrolladas
Se hizo un uso estricto de `structs` para modelar la información académica:

1.  **`BloqueHorario`**: Almacena los datos que caracterizan a cada curso (día, hora_inicio, hora_fin) y también información útil para identificarlos (`codigo_curso`, `grupo`).
2.  **`Grupo`**: Estructura intermedia que agrupa un arreglo de `BloqueHorario`s asociados a un mismo número de grupo, y mantiene un indicador booleano representado con 0 o 1 (`tiene_choque`) específico para esa combinación.
3.  **`Curso`**: Es la estructura principal del programa. Almacena información importante (código, nombre, créditos, semestre), indicadores de estado (aprobado, elegible, tiene_choque), arreglos para almacenar los requisitos y correquisitos y un arreglo anidado de tipo `Grupo` con toda la disponibilidad temporal de la asignatura.

# Proyecto Etapa 2: Generador de Combinaciones de Horario

## 1. Arquitectura del Proyecto
Esta etapa se desarrolló con el paradigma funcional en Typed Racket. El programa toma el catálogo que genera el módulo de C, ya con los choques y la elegibilidad de cada curso calculados, junto con un archivo de preferencias del estudiante para cada carrera. Con eso genera las combinaciones de horario que no tienen choques, las filtra según el rango de créditos que pidió el estudiante y las exporta a un archivo JSON, que es el que va a leer la etapa de Prolog.

El flujo es el mismo para las dos carreras. Primero se leen el catálogo y las preferencias, después se dejan solo los cursos y grupos que le interesan al estudiante, se generan las combinaciones como un stream, se filtran por créditos y al final se exportan. El programa se ejecuta corriendo `main.rkt` desde la carpeta `proyecto-etapa2/src`, ya que las rutas de los archivos son relativas a esa carpeta.

Los módulos principales son:
*   **`main.rkt`**: Archivo orquestador. La función `procesar-carrera` ejecuta el flujo completo para una carrera, y se llama una vez para Computadores y otra para Materiales.
*   **`lectura.rkt`**: Lee el catálogo de C y las preferencias, y los convierte a las estructuras del programa. Solo conserva los cursos que el estudiante puede matricular y que tienen al menos un grupo, porque los demás no pueden formar parte de ninguna combinación.
*   **`choques.rkt`**: Determina si dos grupos se traslapan en el tiempo, comparando sus bloques de horario convertidos a minutos.
*   **`generador.rkt`**: Contiene la implementación de los streams, el filtro de cursos según la lista de interés, el generador de combinaciones y el filtro polimórfico `stream-filtrar`, que usa `filtrar-por-creditos`.
*   **`exportador.rkt`**: Recorre el stream de combinaciones ya filtradas, le asigna un identificador a cada una y escribe el archivo de salida.
*   **`modelo.rkt`**: Define los tipos de datos del programa.
*   **`constantes.rkt`**: Agrupa las rutas de entrada y salida, igual que `constantes.h` en la etapa 1.
*   **`test_lectura.rkt`**: Pruebas por consola de la lectura, los choques, el generador y el filtro por créditos.

## 2. Decisiones de Diseño

### 2.1 Justificación de decisiones propias
Se implementaron streams propios, donde cada elemento guarda el primer valor ya calculado y el resto de la secuencia como una promesa (`delay`). Gracias a esto, ni el generador ni el filtro por créditos calculan combinaciones por adelantado. El stream solo se recorre al final, cuando el exportador lo necesita para escribir el archivo.

El generador funciona como un árbol de decisiones. Para cada curso prueba sus grupos uno por uno y, antes de seguir con el siguiente curso, revisa que el grupo no choque con los que ya se eligieron. Si choca, esa rama se descarta en ese momento y la combinación nunca se termina de armar. Esta optimización solo se pide a los grupos de cuatro integrantes, pero se mantuvo porque evita trabajo innecesario. Los choques se vuelven a calcular en Racket porque el campo `tiene_choque` de C indica si un grupo choca con algún otro del catálogo, pero no dice con cuál, y para armar combinaciones hace falta saber si choca con los grupos elegidos en esa combinación en particular.

La función `stream-filtrar` es polimórfica. No sabe qué tipo de datos hay en el stream ni qué criterio se aplica, solo recibe una función que decide si cada elemento se queda o no. `filtrar-por-creditos` la reutiliza pasándole como criterio una función que revisa si los créditos de una combinación están dentro del rango, y la misma función serviría para cualquier otro criterio. En todo el programa se evitó la mutación. Por ejemplo, el identificador de cada combinación no sale de un contador que se va modificando, sino que se pasa como parámetro y aumenta en uno en cada llamada recursiva.

Para extender los planes de estudio a seis semestres se agregaron los semestres 5 y 6 a los archivos de entrada de la etapa 1, sin tocar su lógica, y se volvió a correr el módulo de C para regenerar los catálogos. Se mantuvo el mismo criterio de datos que antes, el período 2 de 2026 en la sede de Cartago. Se dejaron fuera los grupos de Tutoría y RN, ya que están pensados para estudiantes que repiten el curso y el historial no modela esa situación. Algunos grupos aparecen dos veces en la Guía de Horarios porque los imparten dos profesores, y se dejaron en una sola fila para no duplicar sus bloques de horario. Los historiales se actualizaron para simular un estudiante que entra al semestre 5 con un curso pendiente del semestre 4, así los cursos nuevos se pueden matricular y al mismo tiempo se ve a la validación de requisitos bloqueando otros.

Las preferencias de prueba incluyen más de un grupo por curso, y algunos de esos grupos chocan entre sí a propósito para comprobar que el generador los descarta. En las preferencias de Materiales se incluyó también un curso que el estudiante no puede matricular por requisitos, CM3207, y el programa simplemente lo ignora.

### 2.2 Caso límite real encontrado y resolución
**Caso:** Un grupo por cada curso habilitado deja sin sentido el filtro por créditos.
**Problema:** El enunciado pide combinaciones con un grupo por cada curso habilitado. Si eso se aplica de forma literal, todas las combinaciones tienen los mismos cursos y suman los mismos créditos, así que el filtro por rango deja pasar todas o ninguna. Esto se vio en las primeras pruebas con Computadores, donde los cursos de interés sumaban 11 créditos y el rango pedido era de 12 a 18, por lo que el resultado siempre era cero combinaciones sin importar qué grupos se eligieran.
**Resolución:** Se decidió que el generador permita subconjuntos de cursos. En cada curso se abren dos caminos, incluirlo con alguno de sus grupos compatibles o saltarlo, y esto se controla con el parámetro `permitir-subconjuntos?`. De esta forma salen combinaciones con distintos totales de créditos y el filtro por rango cumple su función. Con los datos actuales, Computadores produce 65 combinaciones entre 12 y 18 créditos. Se conservó también `generar-combinaciones-estrictas`, que solo genera combinaciones con todos los cursos, por si se necesita la interpretación literal.

### 2.3 Justificación del formato de salida
Se eligió **JSON**, el mismo formato de la etapa 1. Cada combinación tiene una cantidad variable de cursos, y JSON lo representa de forma natural con una lista dentro de cada combinación. En un formato plano como CSV habría que repetir los datos de la combinación por cada curso que contiene. Cada curso se exporta como un objeto con `codigo`, `grupo` y `carrera`, en lugar de un arreglo, para que Prolog pueda acceder a cada dato por su nombre sin depender del orden.

Además de los campos obligatorios, se agregó un `id` a cada combinación, porque Prolog va a descartar algunas al aplicar sus reglas y Java necesita una forma de referirse a las que quedaron. También se agregaron `creditos_min`, `creditos_max` y `total_combinaciones` al inicio del archivo, a raíz de un caso que apareció en las pruebas. Cuando ninguna combinación cumple el rango de créditos, el exportador igualmente escribe un JSON válido con la lista vacía, en lugar de dejar un archivo vacío o fallar, y con esos campos queda claro con qué rango se generó y por qué no hubo resultados. Los horarios de cada grupo no se repiten en la salida, ya que están en el catálogo de C y se pueden obtener con el código del curso y el número de grupo.

### 2.4 Validaciones que quedan para Prolog
Las combinaciones exportadas no tienen choques y cumplen el rango de créditos, pero pueden incluir un curso sin su correquisito, por ejemplo CE3201 sin CE1107. El módulo de C ya validó que cada curso por separado se puede matricular, incluyendo sus correquisitos. Revisar que un curso y su correquisito vengan juntos en la misma combinación es una regla de compatibilidad entre cursos, y el enunciado indica que este módulo no debe aplicar reglas de restricción más allá de los créditos, por lo que esa validación le corresponde a la etapa de Prolog.

## 3. Estructuras de Datos Desarrolladas
Todas las estructuras se definen en `modelo.rkt` como `struct` tipados e inmutables.

1.  **`Bloque`**: Un bloque de horario de un grupo. Guarda el día y las horas de inicio y fin convertidas a minutos desde la medianoche, para poder compararlas directamente.
2.  **`Grupo`**: El número de grupo y su lista de bloques de horario.
3.  **`Curso`**: Código, créditos, carrera de origen y la lista de grupos disponibles. Solo se crean para los cursos que el estudiante puede matricular.
4.  **`Pref`**: Las preferencias del estudiante, con los créditos mínimos y máximos y la lista de cursos de interés, cada uno con los números de grupo que desea.
5.  **`Combo`**: Una combinación generada, con los cursos elegidos (código, grupo y carrera) y la suma de sus créditos.
6.  **`Streamof A`**: El tipo de stream polimórfico. Puede estar vacío o tener un primer elemento junto con la promesa del resto.

# Proyecto Etapa 3: Evaluador de Política Académica en Prolog

## 1. Arquitectura del Proyecto
Esta etapa se desarrolló con el paradigma lógico en SWI-Prolog. El programa toma las combinaciones que genera Racket, las carga como hechos y revisa cada una contra una política académica de tres reglas, que son el balance entre carreras, el límite de cursos por área y las incompatibilidades entre cursos. Para cada combinación se indica si cumple la política y, si no la cumple, cuál fue la primera regla que violó. El resultado se exporta a JSON, que es lo que va a leer la etapa de Java.

El código se dividió en tres archivos. En `main.pl` está el flujo principal, que lee los archivos de Racket, convierte cada combinación en un hecho, las evalúa todas y escribe la salida. Ese flujo está en `procesar_carrera`, que se llama tres veces, una para Computadores, otra para Materiales y otra para las combinaciones mixtas. En `reglas.pl` está la lógica de evaluación, con los predicados que suman créditos y agrupan cursos, las tres reglas y el predicado `evaluar/3`, que decide el veredicto y la razón de rechazo. Por último, `politica.pl` solo tiene hechos con los parámetros de la política, así que es el único archivo que hay que tocar para cambiar un porcentaje, el máximo por área o los pares incompatibles.

Igual que en las etapas anteriores, el sistema no es un único ejecutable. Primero se corre el módulo de C, después `main.rkt` desde `proyecto-etapa2/src`, luego se copian los archivos `combinaciones_*.json` de `proyecto-etapa2/data/salida` a `proyecto-etapa3/datos/entradas`, y al final se corre Prolog desde la carpeta `proyecto-etapa3` con `swipl -g main -t halt main.pl`, ya que las rutas son relativas a esa carpeta.

## 2. Decisiones de Diseño

### 2.1 Justificación de decisiones propias

Para esta etapa hubo que extender las anteriores. Los planes de las dos carreras se ampliaron a los primeros 8 semestres agregando los semestres 7 y 8 a los archivos de planes, horarios e historiales de la etapa 1. Con eso Materiales pasaba de 50 cursos, que era el límite anterior, así que `MAX_CURSOS` se subió a 100. El área se agregó como una línea más en cada curso de los archivos de planes, el parser de C la lee y la guarda en un campo nuevo del struct `Curso`, y el exportador la escribe en el catálogo. En Racket el struct `Curso` también recibió el campo `area`, y cada curso de una combinación ahora exporta sus créditos y su área. Antes solo se exportaba el total de créditos de la combinación, pero la regla de balance necesita saber cuántos créditos aporta cada carrera, y eso solo se puede calcular si se conocen los créditos de cada curso. Ninguno de estos cambios toca la lógica que ya existía, solo agregan datos que pasan de una etapa a la siguiente.

También se agregaron combinaciones mixtas. Con las corridas por carrera de la etapa 2, cada combinación tiene cursos de una sola carrera, así que la regla de balance da el mismo resultado para todas. Con un máximo de 100% todas la cumplen y con cualquier valor menor todas la incumplen, por lo que la regla no estaría decidiendo nada. Por eso en Racket se agregó una tercera corrida, `procesar-mixto`, que une los catálogos de las dos carreras con la función `unir-catalogos` y usa las preferencias de un estudiante de Computadores que también lleva cursos de Materiales. El generador y los filtros son los mismos de antes, solo reciben una lista de cursos más grande. Con los datos actuales salen 613 combinaciones mixtas, de las que 151 cumplen la política, 243 se rechazan por balance, 18 por área y 201 por incompatibilidad. Las combinaciones de una sola carrera se siguen evaluando, y con el máximo actual de 70% todas se rechazan por balance, que es justo lo que dice la regla. Si el máximo se sube a 100%, esas combinaciones pasan a revisarse con las otras dos reglas.

Cada combinación se representa con un hecho `combinacion(Id, Cursos)`, donde `Cursos` es una lista de términos `curso(Codigo, Grupo, Creditos, Carrera, Area)`. Se prefirió guardar los cinco datos dentro de cada término, en lugar de tener hechos aparte para cada curso, para que cada combinación quede completa en sí misma y las reglas la puedan recorrer con `member/2` sin consultar nada más. Al leer el JSON se usa la opción `value_string_as(atom)`. Sin ella, SWI-Prolog lee los textos como strings, y un string como `"CE3101"` no unifica con el átomo `'CE3101'` que se usa en la política, de modo que las reglas de balance e incompatibilidad nunca se disparaban. Por la misma razón, los nombres de las carreras en `politica.pl` se escriben exactamente como los exporta C, por ejemplo `'Ingenieria en Computadores'`.

El área de cada curso se asignó según su contenido y no según el prefijo del código. Si se usara el prefijo, todos los cursos CE quedarían en la misma área, y como la mayoría de los cursos de Computadores son CE, casi cualquier combinación se pasaría del límite. Se usaron ocho áreas, que son programación, hardware, redes, matemáticas, física, química, humanidades y ciencias sociales. Por ejemplo, CE1101 Introducción a la programación y CE3101 Bases de datos quedaron en programación, mientras que CE1107 Fundamentos de arquitectura de computadores y CE3201 Taller de diseño digital quedaron en hardware, aunque los cuatro empiecen con CE. De la misma forma, CE1111 Análisis numérico para la ingeniería y CM3207 Métodos numéricos para ingeniería quedaron en matemáticas, junto con los cursos MA. En Materiales los cursos CM se repartieron entre química, como CM3501 Materiales poliméricos, y física, como CM2103 Termodinámica y CM3601 Mecánica de fluidos. Los cursos de inglés y comunicación quedaron en humanidades, y los de gestión y economía, como PI5516 Ingeniería económica o AE4208 Desarrollo de emprendedores, en ciencias sociales. Los cursos que están en los dos planes tienen la misma área en ambos.

Para las incompatibilidades se declararon dos pares por carrera, usando como criterio la carga de trabajo, es decir, cursos del mismo nivel del plan que se consideran muy pesados para llevarlos en el mismo semestre. En Computadores se declararon incompatibles CE3101 Bases de datos con CE3201 Taller de diseño digital, que son del semestre 5 y se evalúan principalmente con proyectos, y MA2105 Ecuaciones diferenciales con CE1107 Fundamentos de arquitectura de computadores, que son los dos cursos de 4 créditos del semestre 5 con más carga de estudio individual. En Materiales se declararon CM3501 Materiales poliméricos con CM4202 Laboratorio de tecnología de aleaciones metálicas, que tienen sesiones de laboratorio e informes, y MI3115 Resistencia de materiales con MI4510 Electrotecnia, que son del semestre 5 y se imparten fuera de la escuela de la carrera. Como la relación es simétrica, cada par se escribe una sola vez en la política y el predicado `son_incompatibles/2` se encarga de revisarlo en los dos sentidos, con una cláusula que busca el par como está escrito y otra que lo busca invertido.

El predicado `evaluar/3` revisa las reglas en el orden balance, área e incompatibilidad, que va de lo más general a lo más específico. La regla de balance mira los créditos de toda la combinación, la de área mira grupos de cursos y la de incompatibilidad mira un par concreto. Con este orden el estudiante recibe primero el problema más amplio, por ejemplo que casi todos sus créditos son de una carrera, antes que un detalle que tal vez se resuelve solo al corregir lo primero.

Las reglas se escribieron con negación por falla. Por ejemplo, una combinación cumple la regla de área si no existe ninguna de sus áreas que pase el máximo, y eso se expresa negando la búsqueda de un área que lo exceda. La primera cláusula de `evaluar/3` devuelve que la combinación cumple cuando las tres reglas se cumplen. Las otras tres cláusulas, una por regla y en el orden mencionado, devuelven que no cumple junto con la razón. Todas terminan con un corte, y ese corte es lo que asegura que solo se reporte la primera regla violada. Sin él, una combinación que viola dos reglas, o la misma regla de dos formas, tendría varias soluciones al hacer backtracking, y como los resultados se recogen con `findall/3`, esa combinación saldría repetida en el archivo con razones distintas.

Un buen ejemplo de cómo el orden cambia la razón es la combinación mixta 17, que tiene CE1107, CE3101, CE3201, CM3501, MI4510 y PI2609. Esta combinación cumple el balance, porque Computadores aporta 10 de sus 18 créditos. Pero tiene tres cursos de hardware, que son CE1107, CE3201 y MI4510, cuando el máximo es 2, y además incluye el par incompatible CE3101 y CE3201. Con el orden actual se reporta que se pasó del límite en hardware. Si en `reglas.pl` se intercambian las cláusulas de área e incompatibilidad, la misma combinación pasa a reportarse como incompatible por CE3101 y CE3201. Con los datos y la política actuales hay 15 combinaciones mixtas en esta misma situación.

Por último, `assertz` solo se usa al cargar las combinaciones del JSON, y `retractall` solo se usa para borrar las combinaciones de un archivo antes de cargar el siguiente. Las dos cosas son parte de la carga de los datos de entrada, que es lo único para lo que el enunciado permite usarlas. Toda la evaluación se hace con argumentos y unificación, sin guardar resultados intermedios.

### 2.2 Caso límite real encontrado y resolución
Al unir los catálogos para las combinaciones mixtas apareció un problema con los cursos que están en los planes de las dos carreras. MA2105 Ecuaciones diferenciales y CS3404 Seminario de ética para la ingeniería, por ejemplo, aparecen en ambos catálogos, y en cada uno tienen grupos disponibles distintos, porque cada carrera tiene su propio archivo de horarios. Con el curso repetido no quedaba claro a qué carrera se le debían contar sus créditos en la regla de balance, ni cuál de las dos listas de grupos había que usar.

Para resolverlo, la función `unir-catalogos` toma completo el catálogo de la carrera principal, que es Computadores, y le agrega solo los cursos de Materiales cuyo código no esté ya en él. Así cada código aparece una sola vez, y un curso compartido siempre se cuenta para la carrera principal y usa los grupos de esa carrera. Se eligió la carrera principal porque, en la práctica, el estudiante matricula ese curso como parte de su propio plan.

### 2.3 Justificación del formato de salida
Se mantuvo JSON, el mismo formato de las etapas anteriores, para que Java pueda leer los archivos de las tres etapas con una sola librería. Además, una combinación tiene una cantidad variable de cursos, y JSON lo representa de forma natural con una lista. Se genera un archivo de evaluaciones por cada archivo de entrada, uno para Computadores, otro para Materiales y otro para las mixtas.

Cada resultado tiene el mismo `id` que la combinación tiene en el archivo de Racket, de modo que Java puede buscar ahí los créditos totales y, en el catálogo de C, los horarios de cada grupo, sin que esos datos se repitan. También se incluyen los pares de código y grupo, para que el resultado se entienda sin abrir otros archivos, un campo `cumple` con el veredicto y un campo `razon`. Cuando la combinación cumple, la razón es `null`. Cuando no cumple, la razón es un objeto con el nombre de la regla violada y una lista con sus datos, por ejemplo la regla `incompatibilidad` con el detalle CE3101 y CE3201. Se exporta como objeto y no como texto para que Java pueda mostrar un mensaje distinto según la regla, sin tener que interpretar la sintaxis de Prolog. La conversión la hace `razon_a_json/2` con el operador `=..`, que separa el nombre de la regla de sus argumentos.

## 3. Representación de Datos y Predicados Principales
Los datos se representan con tres tipos de hechos. Cada combinación de Racket es un hecho `combinacion(Id, Cursos)`, y cada curso dentro de ella es un término `curso(Codigo, Grupo, Creditos, Carrera, Area)`, por ejemplo `curso('CE1107', 1, 4, 'Ingenieria en Computadores', hardware)`. La política se escribe con hechos `max_porcentaje_carrera/2`, que actualmente vale 70 para cada carrera, `max_cursos_area/1`, que vale 2 para todas las áreas, e `incompatible/2`, uno por cada par.

Sobre esos hechos trabajan unos pocos predicados. `creditos_totales/2` y `creditos_por_carrera/3` suman los créditos de la combinación completa o solo los de una carrera. La regla de balance está en `excede_porcentaje/2`, que considera que una carrera se pasa cuando sus créditos multiplicados por 100 superan al máximo multiplicado por el total, comparación que se hace así para evitar divisiones. La regla de área está en `excede_area/2`, que revisa si un área tiene más de N cursos, y la de incompatibilidad en `par_incompatible_en/3`, que busca un par de cursos de la combinación declarado incompatible y usa el orden de los códigos para no encontrar el mismo par dos veces. Cada regla tiene además su versión con negación por falla, que son `cumple_balance/1`, `cumple_area/1` y `cumple_incompatibilidad/1`. Con todo eso, `evaluar/3` decide el veredicto y la razón, y `evaluar_todas/1` recorre por backtracking todas las combinaciones cargadas y recoge sus resultados.

Hay dos predicados que se pueden usar en más de un modo. El primero es `son_incompatibles/2`. Si se le dan los dos códigos funciona como verificación, y por ejemplo `son_incompatibles('CE3101', 'CE3201')` responde que sí. Si se le deja un argumento libre funciona como generador, y `son_incompatibles('MI4510', X)` encuentra que `X` es MI3115. Si se dejan los dos libres, va devolviendo uno por uno todos los pares de la política, en los dos sentidos. El segundo es `excede_area/2`, que puede trabajar en los dos modos porque primero obtiene las áreas que hay en la combinación y después las prueba una por una. Si se le da un área, verifica si esa área se pasa del límite, y si se deja libre, encuentra cuáles se pasan. Con la combinación mixta 17, preguntar por hardware responde que sí, y dejar el área libre devuelve hardware.

Para probar estas consultas se abre `swipl` en la carpeta `proyecto-etapa3`, se carga el programa con `consult('main.pl')` y se cargan las combinaciones con `cargar_combinaciones('datos/entradas/combinaciones_mixtas.json')`. A partir de ahí se puede tomar cualquier combinación con `combinacion(17, C)` y pasarla a las reglas o a `evaluar/3`. Por ejemplo, la combinación 17 se evalúa como incumplida por límite de área en hardware, la 48 cumple todas las reglas, y la 1, que tiene solo cursos de Computadores, se rechaza por balance.
